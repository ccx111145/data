### D-06（MINOR）`<REPOSITORY DOI / URL>` → 完整 URL + 单行修改说明

**文件**：`06_Data_Availability_Statement.txt`（修复前 L12）

**问题**：作者自建 GitHub，但账号名未知；原写法只给了一个语义不明的尖括号 token，
读者无法判断要填 DOI、URL 还是先申请托管，也没有「改哪一行」的指引。

**选择的方案与理由**：给出**完整可读 URL**，只留「账号名」这一个变量，并紧跟一个明确 NOTE：

```
  supplementary material at submission and are archived at
  https://github.com/<YOUR-GITHUB-ACCOUNT>/D-problem-uav-relay
...
------------------------------------------------------------------------
NOTE -- ONE-LINE EDIT BEFORE UPLOAD (only place in this file that
needs changing):
  In the URL above, replace <YOUR-GITHUB-ACCOUNT> with your own
  GitHub account name. The repository must be named D-problem-uav-relay
  and be public; nothing else in this file needs editing. If you
  publish the code under a DOI instead (e.g. Zenodo), replace the
  whole URL with that DOI -- then this NOTE no longer applies.
------------------------------------------------------------------------
```

为什么不在正文里留空、也不编一个假账号：

1. **仓库名已定**（`D-problem-uav-relay`），未知的只有账号名——把它从「找一个 URL」降级为
   「改一处字」，是这里唯一真正能自动化掉的自由度；
2. 全文搜索 `<YOUR-GITHUB-ACCOUNT>` 只能命中这两行（正文 1 行 + NOTE 1 行），改动位置唯一且自解释；
3. 留空或写「see repository」会让这句话在**投稿表单里直接不可用**，作者反而要自己补措辞；
4. 不编造账号名——编错等于给审稿人一个 404 链接，比占位符更糟；
5. 同时给出「改用 DOI」的分支，避免作者被这一行卡住。
   参数集中在 `make_submission_pack.py` 的 `REPO_ACCOUNT_TOKEN` / `REPO_NAME` / `REPO_URL`。

**并且**：`00_上传说明.md` 的待办与「占位符普查」清单里都逐条列出了这个 token 及其行号——
交付文件里不存在「没人知道还剩什么没填」的隐性占位符。
